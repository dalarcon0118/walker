# Estrategia 4D — Duplicidad, Desviación, Diluvio y Disfraz

- **Estado:** estrategia propuesta (2026-11-24).
- **Decisión:** [ADR-WALKER-086](ADR-WALKER-086-work-contract-cuatro-controles.md).
- **Implementación:** [SPEC-WALKER-045](SPEC-WALKER-045-work-contract-agent-controls.md).
- **Bucle:** usuario → agente → walker → harness.

Este documento es la **estrategia**; el ADR fija la decisión y sus invariantes, y
la spec baja la estrategia a fases, gates, tests y criterios de aceptación. No
se duplican: cada uno tiene un rol distinto.

## Principio

La forma correcta de atacarlo no es agregar cuatro tools nuevas, sino agregar
**cuatro contratos de control** al bucle `usuario → agente → walker → harness`,
cada uno en la capa donde vive la información o la decisión. Si lo hacemos como
cuatro features separadas, vamos a reproducir el problema de duplicidad dentro
del propio mecanismo.

La idea central es un artefacto único por spec, el **`WorkContract`**,
persistido en `spec.task_context.contract`. No es una entidad nueva del dominio:
es la vista operativa de datos que ya existen en Delta, CKG, CPG y Trace. El
agente lo propone, el usuario lo aprueba, walker lo guarda y el harness lo hace
cumplir.

```json

    "original_intent": "pedido original del usuario",
    "version": 1,
    "approved_by": "user",

  },
  "task": {
    "spec_id": "SPEC-001",
    "objective": "...",
    "scope": ["archivo/a.py", "archivo/b.py"],
    "budget": {"max_files": 3, "max_loc": 200, "max_new_files": 1}
```

Con ese contrato, cada capa tiene una responsabilidad clara: el **usuario**
decide y aprueba, el **agente** propone y ejecuta, **walker** persiste e impone
invariantes, y el **harness** observa, inyecta y bloquea. Ninguna capa debe
hacer el trabajo de otra.

## Mapa por capa

| Problema | Usuario | Agente | Walker | Harness |
| :--- | :--- | :--- | :--- | :--- |
| **Duplicidad** | decide reutilizar o crear | corre `reuse_scan` y elige con evidencia | CKG + Delta + CPG buscan similitud | inyecta candidatos y bloquea código nuevo sin scan |
| **Desviación** | confirma goal y aprueba cambios | mantiene el goal y declara a qué criterio sirve cada write | `goal → spec → criterio → archivo` trazable | reinyecta el goal cada turno y detecta drift |
| **Diluvio** | aprueba un lote del tamaño de una spec | trabaja una spec y se detiene en el budget | budget por spec + review obligatorio | cuenta writes/files y fuerza review |
| **Disfraz** | acepta con evidencia, no con relato | mapea cada criterio a un predicado | manifest de verificación + cierre revalidado | bloquea “done” sin verde y detecta recurrencia |

## 1D — Duplicidad

No es un problema de memoria: es un problema de **búsqueda no obligatoria**. El
agente duplica porque leer es opcional y escribir es barato. La solución es
hacer que el `DESIGN_ANALYZE` tenga un campo obligatorio `reuse_decision` y que
el `brief`/`preflight` devuelva un bloque `reuse` con tres señales fusionadas:
Delta busca specs/tareas similares por objetivo, `problem_statement` y
archivos; CKG busca decisiones, convenciones y ADRs que apliquen al mismo
componente; CPG busca símbolos, call graph y funciones candidatas a reutilizar
o extender. Si el agente elige `new`, tiene que explicar por qué los candidatos
no alcanzan; si hay un candidato con similitud alta, el PO puede exigir un
waiver. En `CODE_REVIEW_SCAN`, un detector de clones o de funciones
equivalentes marca la violación. El harness mete los candidatos en el flight
card y, si el agente intenta crear un archivo o símbolo nuevo sin un evento
`reuse_scan` para esa tarea, lo bloquea con el comando exacto para hacer el
scan. Eso convierte “revisar si ya existe” en el camino más barato, no en una
virtud.

## 2D — Desviación

Tampoco es un problema de prompt: es un problema de **atención** que se degrada
turno a turno. El `WorkContract` fija el goal, el `session_plan` lo baja a
tarea/alcance/criterios y el Delta mantiene la cadena
`sprint goal → spec objective → acceptance criterion → archivo → test`. En cada
checkpoint (`SPRINT.ACTIVE`, `DESIGN_REVIEW`, `USER_GATE`, `REPORT_GATE`,
`PO_ACCEPT`) walker verifica que la tarea actual siga colgando de ese goal; si
no, no permite seguir por el flujo normal: exige `session_plan` con `goal_delta`
aprobado por el usuario o el gate `goal_invalidation`. El harness reinyecta en
cada turno una línea corta de anclaje —goal, criterio actual, próximo paso— y
detecta dos señales: escritura fuera del scope y cambio de tema del usuario con
baja superposición respecto del goal. Ante cualquiera de las dos, no bloquea de
entrada: inyecta “posible cambio de goal” y obliga a declarar si es continuidad
o invalidación. La diferencia es importante: el agente no debe poder cambiar el
goal por accidente, pero el usuario sí debe poder cambiarlo explícitamente.

## 3D — Diluvio de código

El problema es que el tamaño del lote no está acotado. La unidad de revisión
tiene que ser la **spec**, no el sprint ni la sesión. Cada spec declara
`budget` (máximo de archivos, líneas y archivos nuevos) y el workflow
`WORK → CODE_REVIEW_SCAN → CODE_REVIEW_RESULT → MONITORING → REPORT_GATE` se
convierte en el punto de corte. Si el diff excede el budget, el agente no sigue
escribiendo: tiene que dividir la spec o pedir aprobación explícita.
`CODE_REVIEW_RESULT` y `REPORT_GATE` exigen `review_verdict`, findings y el diff
revisado; `SPRINT.REVIEW` agrega las reviews de todas las specs, y
`SPRINT.CLOSE` no cierra si hay specs con review pendiente o diffs sin revisar.
El harness ya cuenta writes y archivos tocados; lo que falta es usar ese
contador como gate: al llegar al budget, niega más `edit`/`write` hasta que
haya un `code_review` o una ampliación aprobada. El flight card muestra “batch
2/3 archivos, 140/200 líneas, próxima review”, y `what_changed`/`plan_diff` se
inyectan en la review para que el usuario no tenga que reconstruir el diff.

## 4D — Disfraz

Es el más caro porque un falso “done” contamina la confianza en todo el
mecanismo. La regla debe ser: **sin manifest, no hay `completed`; sin
revalidación, no hay `close`**. En `PLAN_APPROVAL`/`TASK_SPEC`, cada criterio de
aceptación debe estar mapeado a un predicado ejecutable; `spec_predicates` ya
soporta `unmapped`, pero hoy el validador acepta “criterios o predicados” sin
exigir que todos los criterios estén cubiertos. En `VERIFY.PREDICATE_CHECK`,
`verify_predicates` debe correr sobre el commit actual y guardar un
`verification_manifest` con criterio, comando, resultado, commit, revisión,
timestamp y runner. `PO_ACCEPT` no puede pasar a `completed` si el manifest no
está verde o si el commit cambió después de verificar. `SPRINT.CLOSE` tiene que
revalidar los manifests de todas las specs completadas: si el código cambió
después del verde, la verificación está stale y el cierre se bloquea. La
revisión independiente ya existe (`reviewed_by` distinto del autor), pero debe
formar parte del mismo manifest. Y para el “dos sesiones después aparece el
mismo problema”, el Delta y el CKG necesitan detectar recurrencia: si el nuevo
`problem_statement` o los síntomas se parecen a una spec anterior, no se crea
una spec nueva que esconda el fallo; se reabre la anterior con `reopen_reason`
y se exige un predicado de regresión. El CKG guarda el hecho
`fallo → causa raíz → fix → test de regresión`, y el `session_bind resume` lo
muestra al inicio de la sesión siguiente.

## Fases de implementación

La implementación debería hacerse en cuatro fases, no en un big bang:

1. **Proyección y medición:** extender `brief`/`preflight` para devolver
   `contract`, `reuse`, `budget`, `verification` y `recurrence`, sin bloquear
   nada, y emitir eventos de Trace (`reuse_scan`, `drift_detected`,
   `budget_exceeded`, `criteria_unmapped`, `verification_stale`, `false_done`).
2. **Contratos en el workflow:** `DESIGN_ANALYZE` exige `reuse_decision`;
   `TASK_SPEC` exige criterios mapeados; `VERIFY` escribe el manifest.
3. **Gates duros del harness:** no crear código nuevo sin scan, no seguir
   escribiendo sin budget/review, no declarar `completed` sin manifest, no
   cerrar con verificación stale.
4. **Aprendizaje:** detector de clones, grafo de recurrencia y reapertura
   automática.

La secuencia importa: ADR-084 ya mostró que un gate que solo cobra y no ofrece
remedio entrena al agente a ignorarlo. Cada gate nuevo tiene que inyectar el
comando exacto que lo desbloquea.

## Regla de diseño

Hay una regla que evitaría repetir el problema de duplicidad en el propio
mecanismo: **un solo lector** (`brief`) y **un solo escritor de evidencia**
(`capture`/`spec_status`). Los cuatro controles son campos, gates y eventos
sobre ese contrato; no cuatro tools nuevas. Eso mantiene el bucle
`usuario → agente → walker → harness` con una sola fuente de verdad por
decisión.
